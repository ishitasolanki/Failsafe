Track 03 · AI Revenue Recovery

It knows when not to retry.

When a payment fails on Razorpay, the merchant loses the sale silently. Failsafe diagnoses why it failed, picks a bounded recovery action, and stops when stopping is the right answer — because retrying a revoked mandate is a compliance breach, not a second chance.

60 held-out payments measured against a naive-retry baseline reproducible with zero API keys

Payments don't just fail. Each one fails differently.

Merchants today run one blanket “retry tomorrow”, or nothing at all. But the right move depends entirely on the cause — and for two of these six, the right move is to do nothing.

Does the model earn its place?

The LLM has exactly one job: name the cause. It never chooses the money action. So the fair question is whether it beats a keyword lookup over the error string — measured, not assumed.

Safety does not sit downstream of the model

Learned the hard way. An early run showed 9 compliance violations even though the policy refuses to retry revoked mandates — because a fraud case misdiagnosed as insufficient funds arrives already wearing the wrong label. Two guards now run without consulting the diagnosis at all: an abnormal failure burst stops a payment outright, and a recurring payment has its mandate looked up rather than guessed. Violations went 9 → 0.

What is real and what is simulated

Payment links & ordersreal test-mode API
Failure diagnosisreal LLM calls, cached
Policy, stopping rules, auditreal code
The failed paymentssynthetic
Whether a customer then payssimulated

Test mode cannot make a customer pay, so outcomes come from a pre-rolled world whose assumptions sit in one readable table at the top of seed.py — stated so they can be disagreed with. Customer messages are generated and rendered, never sent.
